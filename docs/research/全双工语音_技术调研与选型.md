# 全双工语音 · 技术调研与选型

> 主题：为「聊天模式」升级为全双工实时语音对话（类似豆包通话，AI 是有人格 + 先验知识的口语辅导老师）做技术选型
> 日期：2026-08-19
> 状态：调研完成，选型建议待用户最终确认
> 关联文档：《口语部分产品形态_聊天模式与备考模式.md》阶段 D

---

## 0. 一句话结论

全双工语音有三条可用链路，都已成熟。**推荐「方案 B：自建流式管道」为主路径**——豆包双向流式 ASR（Doubao-Seed-ASR-2.0）+ DeepSeek 流式生成 + 豆包双向流式 TTS，用 VAD + 打断信号实现全双工。

**核心理由**：产品灵魂是「懂教学、有人格、有先验知识」的老师，教学法（选择性纠错、复述示范、中文讲解）与先验知识（学生画像 + 场景 + 人设 + 历史记忆）**都必须在 LLM 层精细可控**。端到端 Realtime API 虽然最自然，但其人格配置仅 1500 字符、无法注入完整教学逻辑，与产品定位有张力。

---

## 1. 需求约束（选型的前置条件）

选型不是选"最快"或"最炫"，而是选"最贴合产品定位"。本项目的硬约束：

| 约束 | 说明 |
|---|---|
| **教学法必须可控** | 选择性纠错（按严重度混合：影响理解立即打断、小错听完再纠）、复述示范、苏格拉底式引导，都是精细逻辑，不能被模型"黑盒"吞掉 |
| **先验知识必须可注入** | 学生 CEFR + 薄弱点、本课场景 + 教学点、老师人设、历史对话记忆——要完整塞进 system prompt，而非 1500 字的摘要 |
| **允许夹杂中文** | 讲解/纠错用中文、练习用英文——中英混说能力要稳定 |
| **音色可定制** | 已选定豆包音色 `en_female_myra_cmb_uranus_bigtts`，希望延续 |
| **成本可控** | 面向学生的学习产品，长期跑量，单价敏感 |

## 2. 三条链路调研

### 2.1 方案 A：豆包端到端实时语音大模型（Realtime API）

**已确认事实**（来源：火山引擎官方文档 `docs/6561/1594356` 及第三方接入文档）：

| 项目 | 内容 |
|---|---|
| WebSocket 地址 | `wss://openspeech.bytedance.com/api/v3/realtime/dialogue` |
| 鉴权 Header | `X-Api-App-ID`、`X-Api-Access-Key`、`X-Api-Resource-Id`（固定 `volc.speech.dialog`）、`X-Api-App-Key`（固定 `PlgvMymc7f3tQnJ6`）、`X-Api-Connect-Id`（UUID） |
| 上传音频 | PCM 16kHz / int16 / 单声道 |
| 返回音频 | 默认 OGG/Opus；可在 `StartSession.tts.audio_config` 配成 PCM 24kHz / Float32 |
| 打断 | 支持：`ASRInfo`（事件 450）= 识别到首字，可打断客户端播报；`server_vad` 模式 |
| 人格配置 | `StartSession.dialog`：`bot_name`（≤20 字）、`system_role`（背景人设）、`speaking_style`（风格）、`dialog_id`（会话续接） |
| **人格长度限制** | **`system_role` + `speaking_style` 合计 ≤ 1500 字符** |
| 半接管能力 | `SayHello`（300）= 客户端提交打招呼文本；`ChatTTSText`（500）= 客户端指定文本合成音频 |
| 关键事件流 | `StartSession`(100) → `SessionStarted`(150, 返回 `dialog_id`) → `TaskRequest`(200) 传音频 → `ASRInfo`(450)/`ASRResponse`(451)/`ASREnded`(459) → `ChatResponse`(550)/`ChatEnded`(559) → TTS 事件(350/351/352/359) |
| 延迟/定价 | 官方仅称「超低延时」，无公开具体数字；无公开定价细节，需以控制台账单为准 |

**优势**：
- 端到端，链路最短，延迟最低，最接近「豆包通话」自然体验。
- 打断、VAD、语轮切换由服务端原生处理，客户端只需收发音频，**开发量最小**。
- 支持 `dialog_id` 会话续接，天然有"对话记忆"。

**劣势（对本品致命）**：
- **人格 1500 字限制**：塞不下「学生完整画像 + 薄弱点 + 课程计划 + 教学法规则」。
- **教学控制不可精细**：端到端模型内部自行决定何时纠错、怎么纠错，我们无法注入"按严重度混合纠错""复述示范""中文讲解"这类教学逻辑。
- 音色/人格定制能力弱，与"外教老师"的长期人格塑造有冲突。
- 成本、延迟不透明，难以做容量与预算规划。

### 2.2 方案 B 组件一：豆包流式语音识别 ASR

**已确认事实**：

| 项目 | 内容 |
|---|---|
| 模型 | `Doubao-Seed-ASR-2.0`（火山引擎 2025-12-05 发布） |
| 双向流式识别 | WebSocket，实时逐字返回识别结果，**适合实时对话**（全双工必须用这种） |
| 单向流式识别 | WebSocket，流式输入、返回**整句**识别结果，准确率高于双向流式，但**非实时**（适合语音输入法、微信语音转文字） |
| 音频 | 流式 PCM 上传（与 Realtime 一致，16kHz 为主） |

> ⚠️ 关键区分：文档里「双向流式识别」和「单向流式识别」是两个不同接口。**全双工对话要用「双向流式」**（逐字实时），不能用「单向流式」（它要等整句说完才返回，语义上就是非实时）。

**结论**：豆包 ASR 的实时流式能力已具备，与"待写 adapter"的既有记忆一致——后续需在 nanobot 中新增豆包双向流式 ASR 的 adapter（当前 ASR 走硅基流动）。

### 2.3 方案 B 组件二：豆包流式语音合成 TTS

**已确认事实**：

| 项目 | 内容 |
|---|---|
| 双向流式 TTS WebSocket | 文本流式输入 + 音频流式输出，低时延，**适用于实时交互**（火山官方文档 `docs/6561/2532486`） |
| 单向流式 TTS WebSocket V3 | 文本输入 + 音频流式输出（`docs/6561/1329505`） |
| HTTP Chunked/SSE 单向流式 V3 | HTTP 流式输出（`docs/6561/1598757`） |
| 当前实现 | `services/tts/doubao.py` 用 **V1 非流式 HTTP**（`/api/v1/tts`），一次性返回整段 mp3 |

**结论**：全双工需要把 TTS 从"整段合成"升级为"流式合成"。豆包**双向流式 TTS**（文本流式进、音频流式出）是目标组件；作为过渡，也可先用"单向流式 TTS"（拿到 LLM 完整回复后流式下发音频），牺牲一点首字延迟换取实现简单。

## 3. 三方案对比（选型核心）

| 维度 | A. 端到端 Realtime | B. 自建流式管道（ASR+LLM+TTS） | C. 混合（Realtime + LLM 控制层） |
|---|---|---|---|
| 自然度 / 延迟 | ★★★★★ 最低 | ★★★ 三段式，略高 | ★★★★ 介于两者 |
| **教学法可控性** | ★ 黑盒，不可精细控 | ★★★★★ LLM 层全可控 | ★★★ 半可控 |
| **先验知识注入** | ★ 1500 字限制 | ★★★★★ 完整 system prompt | ★★★ 受 Realtime 侧限制 |
| 人格塑造能力 | ★ 有限 | ★★★★★ 完全由 prompt 决定 | ★★★ 受 Realtime 侧限制 |
| 音色延续 | ✗ 音色体系不同 | ✓ 复用豆包 TTS 音色 | △ 视接管方式 |
| 开发量 | ★ 最小 | ★★ 较大（要写 ASR adapter + 流式编排 + VAD） | ★★★ 最大 |
| 成本可控性 | 不透明 | 可控（按 token/时长明码） | 不透明 |
| 复用现有资产 | 几乎不 | 复用 DeepSeek + 豆包 TTS + 现有双轨评分 | 部分 |

### 选型结论

**主路径：方案 B（自建流式管道）。**

理由（按优先级）：
1. 教学法（选择性纠错、复述示范、中文讲解）是产品核心差异化，**必须在 LLM 层可控**，Realtime API 做不到。
2. 先验知识（学生画像 + 场景 + 人设 + 记忆）要完整注入，1500 字不够。
3. 复用现有资产（DeepSeek 封装、豆包 TTS、`analyze_speech` 双轨评分、progress 表），演进成本最低。

**进阶优化（Phase 2+ 再评估）：方案 A 的 `ChatTTSText`（500）/`SayHello`（300）半接管能力**——未来若追求更低延迟，可让 Realtime 承担"自然倾听 + 快速应答"，在关键节点（纠错、示范、教学推进）由我们的 LLM 层通过 `ChatTTSText` 接管 TTS 输出，实现"低延迟 + 精确教学"的折中。这是后话，先不投入。

## 4. 待调研 / 待确认项（不影响主路径选择，但影响工作量）

| 待确认 | 说明 | 影响 |
|---|---|---|
| 豆包双向流式 ASR 的具体协议 | 事件格式、鉴权 Header、采样率、是否支持中文混说 | 决定 ASR adapter 实现 |
| 豆包双向流式 TTS 的具体协议 | 是否支持逐字/分句流式输出、音色是否复用现有 `en_female_myra_cmb_uranus_bigtts` | 决定 TTS 流式化改造 |
| 端到端延迟预算 | 三段式（ASR 首字→LLM 首 token→TTS 首帧）的实际延迟 | 决定是否要做流式叠加优化 |
| 前端音频栈 | WebRTC/WebSocket 采集、VAD、回声消除（AEC）、打断 | 决定阶段1→全双工的工程边界 |
| 成本 | 豆包流式 ASR 按小时计费（约 4.5 元/小时）、TTS 按字符、DeepSeek 按 token | 决定是否需要对流式做时长统计 |

---

## 5. 落地路径（与阶段规划对齐）

```
阶段 1（可打断半双工，本计划交付）：前端 VAD 打断 TTS 播报，后端回合制复用
   ↓ 积累 VAD 与音频状态管理经验
阶段 2（全双工 MVP）：豆包双向流式 ASR adapter + DeepSeek 流式 + 豆包流式 TTS
   ↓ 打通三段式流式管道
阶段 3（精细化）：按严重度混合纠错 + 先验知识注入 + 人格塑造 + Realtime 半接管评估
```
