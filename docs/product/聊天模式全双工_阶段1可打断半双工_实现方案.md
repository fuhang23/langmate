# 聊天模式全双工 · 阶段1「可打断半双工」实现方案

> 主题：全双工第一阶段——先实现「学生说话即打断 AI 播报」，保留回合制后端，为全双工流式管道铺路
> 日期：2026-08-19
> 状态：方案设计完成，待实施
> 关联文档：《口语部分产品形态_聊天模式与备考模式.md》《聊天模式全双工_产品形态与人格设计.md》《全双工语音_技术调研与选型.md》

---

## 0. 一句话结论

阶段1 **不动后端回合制**（ASR → LLM → TTS 复用），只在**前端**实现「学生开口即打断正在播放的 AI 语音」：新增一个轻量 VAD（麦克风能量检测）+ 一个统一的音频播放管理器，让学生想插话时 AI 立刻闭嘴。这一步价值是**积累 VAD 与音频状态管理经验**，为阶段2 的全双工流式管道打地基。

---

## 1. 为什么阶段1只做前端

| 理由 | 说明 |
|---|---|
| 风险隔离 | 全双工最大不确定性在前端（VAD、打断、音频状态），先单独验证，避免和后端流式改造耦合 |
| 复用后端 | 回合制 ASR→LLM→TTS 已跑通，不重写，只让"学生说话"这个信号去控制前端的音频播放 |
| 明确交付 | 一个可感知的体验升级：AI 说话时学生能随时打断，不再是"等 AI 说完才能说" |

## 2. 现状分析（代码锚点）

### 2.1 聊天模式 TTS 音频如何被播放

链路：`SpeakTool`（`app/tools/speak_tool.py`）→ 豆包 TTS 合成 mp3 → 存 `media/tts/` → `OutboundMessage.media` 投递 → 前端 `MessageBubble` → `AttachmentTile`。

**关键现状**：`AttachmentTile.tsx`（第 55-78 行）把音频渲染成**原生 `<audio controls>`**，是**手动点击播放**，不是自动播放：

```55:78:app/nanobot/webui/src/components/AttachmentTile.tsx
  if (attachment.kind === "audio" && hasUrl && !failed) {
    return (
      <AttachmentFrame ...>
        <audio
          src={attachment.url}
          controls
          preload="metadata"
          ...
        />
      </AttachmentFrame>
    );
  }
```

**含义**：聊天模式当前"AI 说话"其实是"AI 发一段音频 + 学生手动点播放"。这离"真实外教课"还有距离——外教是**自动开口说话**，学生随时能插话。

### 2.2 已有的能量检测能力（VAD 的基础）

`useVoiceRecorder.ts` 已经在录音时用 `AnalyserNode` 计算麦克风能量：

```98:139:app/nanobot/webui/src/hooks/useVoiceRecorder.ts
      ...

```

以及能量计算函数：

```375:384:app/nanobot/webui/src/hooks/useVoiceRecorder.ts
function voiceLevelFromSamples(samples: ArrayLike<number>): number {
  ...
  const rms = Math.sqrt(sum / samples.length);

```

**含义**：能量检测的核心逻辑已存在，只是当前**只在录音时才启动**。阶段1要把它抽出来，做成一个**持续监听**的 VAD，不管是否在录音。

### 2.3 自动播放的参考实现

`RepeatPlayer.tsx`（第 91-106 行）的 `playDemo` 用 `new Audio(url).play()` 自动播放，但**没有保存 Audio 引用**，无法中途打断：

```91:106:app/nanobot/webui/src/components/toefl/RepeatPlayer.tsx
  const playDemo = useCallback(async () => {
    ...
      const audio = new Audio(url);
      await audio.play();
    ...
  }, [currentSentence, playing, getToken]);
```

**含义**：要做"可打断"，必须先有**全局唯一的播放管理器**，保存当前播放的 Audio 引用，支持 `stop()`/`pause()`。

## 3. 方案设计

### 3.1 总体架构（阶段1）

```
┌─────────────────────────────────────────────────────────┐
│ 前端                                                      │
│                                                          │
│  useVoiceActivityDetector（新，持续监听麦克风能量）      │
│        │ 检测到学生开口（能量 > 阈值 + 持续 N ms）        │
│        ▼                                                 │
│  audioPlaybackManager.stop()（新，停止当前 AI 语音）     │
│                                                          │
│  AI 语音播放：改为走 audioPlaybackManager（自动播放）    │
└─────────────────────────────────────────────────────────┘
```

### 3.2 新增组件一：`useVoiceActivityDetector`（VAD hook）

**职责**：独立于录音流程，持续监听麦克风能量，判定"学生是否在说话"。

**要点**：
- 复用 `useVoiceRecorder` 里的 `AnalyserNode` + `voiceLevelFromSamples` 逻辑，抽成公共工具函数（如 `lib/voice.ts`）。
- 触发条件：`level > SPEECH_THRESHOLD` 且持续 `HOLD_MS`（避免咳嗽/杂音误触发）。建议初始阈值参考 `VOICE_MIN_LEVEL = 0.018`，上调到 0.03~0.05，需实机调。
- 触发后回调 `onSpeechStart`（打断 AI 语音）。
- 可选：增加 `onSpeechEnd`（静音持续 N ms），为阶段2 全双工"自动断句"预留。
- **权限复用**：与录音共用同一个 `getUserMedia` 流，避免重复申请麦克风权限。

**输出状态**：`isSpeaking`（布尔）、`onSpeechStart` 回调、`start()`/`stop()` 控制。

### 3.3 新增组件二：`audioPlaybackManager`（播放管理器）

**职责**：全局唯一的 AI 语音播放控制点，保存当前播放引用，支持打断。

**要点**：
- 模块级单例（或 React Context），提供 `play(url)` / `stop()` / `pause()`。
- `play()` 时若已有音频在播，先停旧的（同一时刻只播一段）。
- `stop()` 被 VAD 触发时，立即 `audio.pause()` 并释放资源。
- 参考 `RepeatPlayer.playDemo` 的 `URL.createObjectURL` + `new Audio()` 模式，但把 Audio 引用挂到管理器上。

### 3.4 改造点：聊天音频自动播放 + 可打断

把 `AttachmentTile` 里聊天模式的 `<audio controls>` **在聊天模式场景下改为自动播放**，或更稳妥：新增一个 `AssistantAudioBubble` 组件（聊天模式专用），渲染为"可打断的自动播放语音条"：

| 现状 | 目标 |
|---|---|
| 原生 `<audio controls>`，手动播放 | 自动播放，播放条仍保留进度/重播按钮 |
| 无全局引用，无法打断 | 走 `audioPlaybackManager`，可被 VAD 打断 |
| 学生只能在 AI 说完后说话 | 学生一开口，AI 语音立即停 |

> ⚠️ **自动播放策略**：浏览器要求用户先有手势交互才能自动播放声音。聊天模式进入时需有"开始对话"按钮，或复用现有发送消息的手势，解锁 AudioContext 后自动播放才生效。这是阶段1要处理的一个细节坑。

### 3.5 打断后的行为（产品语义）

- 学生打断后，AI 语音停止，学生**立即进入可录音状态**（或仍需按住说话——阶段1保留"按住说"，只让打断更灵敏）。
- 后端回合制不变：学生说完整句 → ASR → LLM → TTS 新一段。
- 体验变化：**学生不用等 AI 说完**，想插话就开口（或按住）。

## 5. 验收标准

- [ ] 聊天模式下，AI 语音自动播放（无需手动点）。
- [ ] 学生开口说话（或按住录音），正在播放的 AI 语音**立即停止**。
- [ ] 打断后学生能正常录音并得到 AI 回复（回合制闭环完整）。
- [ ] 不打断时，AI 语音完整播完，不影响原有流程。
- [ ] 备考模式（跟读/面试）不受影响。

## 6. 风险与边界

| 风险 | 应对 |
|---|---|
| 浏览器自动播放策略 | 用"开始对话"手势解锁 AudioContext；兜底保留手动播放按钮 |
| VAD 误触发（咳嗽/环境噪音） | 阈值 + 持续时长双重判定，实机调参；先做"按住说打断"最简版，VAD 作为增强 |
| 麦克风权限重复申请 | 与录音共用 `getUserMedia` 流，进入聊天模式时一次性授权 |
| 回声（AI 语音被自己的麦克风收进去） | 阶段1 影响小（打断是单向的）；阶段2 全双工需做 AEC，本文档记录为待办 |

---

## 7. 与阶段2 的衔接

阶段1 沉淀的 `useVoiceActivityDetector`（含 `onSpeechStart`/`onSpeechEnd`）与 `audioPlaybackManager`，正是阶段2 全双工流式管道的两块基础积木：
- `onSpeechEnd` → 自动断句，触发 ASR。
- `audioPlaybackManager` → 升级为"流式音频缓冲播放"（边收边播），支持逐帧打断。

因此阶段1 虽只做前端，但**接口设计要按阶段2 的需求预留**，避免返工。
